# perceptron_robot_gazebo

The simulated environment: the world the robot spawns into and the ArUco docking
station it drives at. The robot model itself lives in
`perceptron_robot_description`.

```
worlds/
  docking_world.world        minimal: ground plane + dock, for docking tests
  room_world.world           8 x 6 m room with obstacles, for SLAM and Nav2
                             GENERATED by tools/gen_world.py - edit that, not this
models/
  aruco_dock_station/
    model.config
    model.sdf
    materials/scripts/aruco.material
    materials/textures/aruco_marker_42.png
launch/
  gazebo.launch.py           standalone, empty world (not used by the docking sim)
```

The docking simulation is launched from `perceptron_robot_bringup`; this package
only supplies the assets.

## SDF is not URDF

The single biggest source of silent failure in this package. SDF and URDF look
similar and share none of the important syntax.

| | URDF | SDF |
| --- | --- | --- |
| Pose | `<origin xyz="1 0 0" rpy="0 0 0"/>` | `<pose>1 0 0 0 0 0</pose>` |
| Size | `<box size="1 2 3"/>` | `<box><size>1 2 3</size></box>` |
| Unknown tags | error | **silently ignored** |

The dock model originally used URDF `<origin>` tags. SDF ignored them, so the
post, the backing board and the marker plate all collapsed onto the model
origin: half buried in the ground plane, with the marker *inside* the post. No
warning, no error, just a camera that never saw a marker.

If a model looks wrong in Gazebo, check that every element has a `<pose>` and
not an `<origin>`.

## docking_world.world

| element | why it is the way it is |
| --- | --- |
| `<light name="sun">` and an inline `ground_plane` | Written out rather than `<include><uri>model://sun</uri>`. Combined with `GAZEBO_MODEL_DATABASE_URI=""` in the launch file, this guarantees Gazebo never reaches for the online model database, which otherwise stalls startup for ~30 s on a cold machine. |
| Dock at `<pose>2.0 0 0 0 0 3.14159265</pose>` | The marker faces the model's +X, so a yaw of pi turns it back towards a robot spawning at the origin. |
| `<plugin name="gazebo_ros_state" filename="libgazebo_ros_state.so">` | Ground truth on `/gazebo/model_states` and `/gazebo/get_entity_state`. This is a **world** plugin, so it belongs in the world file — passing it to `gzserver -s` (which only takes *system* plugins) silently does nothing. |
| ODE `iters 75`, `contact_surface_layer 0.001` | Stiffer contact solving so a 4-wheel skid-steer does not jitter on the ground plane. |

Ground truth is worth knowing about: it is how you tell a control bug from a
perception bug. If odometry says the robot is docked and `model_states` says it
is 20 cm away, the problem is the drivetrain calibration, not the docking law.

```bash
ros2 topic echo /gazebo/model_states --once
```

## The ArUco docking station

```
        +X  (marker faces this way)
         ^
         |    [====]  marker plate   0.1875 m, at z = 0.162 m
         |    [######] white backing  0.25 m
      [########]      post 0.08 x 0.34 x 0.34, centre z = 0.17
      [########]
  ----------------- ground
```

| part | size | pose (model frame) |
| --- | --- | --- |
| Post (visual + collision) | 0.08 × 0.34 × 0.34 | `0 0 0.17` |
| White backing board | 0.005 × 0.25 × 0.25 | `0.0425 0 0.162` |
| Marker plate | 0.002 × 0.1875 × 0.1875 | `0.0455 0 0.162` |
| Contact plate (cosmetic) | 0.006 × 0.16 × 0.05 | `0.0425 0 0.033` |

The marker centre is at **z = 0.162 m**, deliberately equal to the camera height
(0.1621 m), so the marker stays vertically centred in frame through the whole
approach.

### Marker size arithmetic — get this wrong and every distance is wrong

`aruco_marker_42.png` is 500 × 500 px and the black marker square occupies the
middle **400 px, i.e. 80%**; the rest is the white quiet zone the detector needs.
A Gazebo `<box>` stretches the texture across the whole face, so:

```
printed marker size = plate size × 0.8
0.1875 m plate      → 0.15 m marker   ← matches marker_size in docking_params.yaml
```

`solvePnP` scales distance linearly with the assumed marker size, so a plate that
renders a 0.144 m marker while the detector is told 0.15 m puts a 4% error on
every range estimate. The original 0.12 m plate did exactly that.

**If you change the plate size, change `marker_size` in
`perceptron_docking/config/docking_params.yaml` to match — and vice versa.**

Verify against ground truth rather than trusting the arithmetic:

```bash
bash tools/rangetest.sh 1.55     # parks at ~0.40 m, compares to model_states
```

Currently reads within 0.2% at 0.40 m and 0.01% at 1.95 m.

### Sizing a marker for a different camera

The marker is squeezed between two limits:

- **Detection floor.** ArUco needs roughly 4 px per module; a `DICT_5X5` marker
  is 7 modules across including its black border. So the marker must span about
  28 px at the furthest point of the approach, including foreshortening when
  seen off-axis. A 0.10 m marker at 2 m, 40° off-axis, on a 640×480 / 80° camera
  is only ~15 px — the dock vanishes mid-approach and the robot circles forever.
- **Field-of-view ceiling.** The marker must still fit in frame at the visual
  stop distance. Vertical is the tighter constraint on a 4:3 sensor:
  `min_camera_distance = (marker_size / 2) / tan(vfov / 2)`. For 0.15 m and this
  camera that is 0.119 m, so `base_footprint` cannot be closer than about 0.30 m.

That ceiling is why the docking controller stops its visual servo at 0.40 m and
dead-reckons the rest.

### Making a different marker

```bash
python3 - <<'PY'
import cv2, cv2.aruco as aruco
d = aruco.getPredefinedDictionary(aruco.DICT_5X5_250)
img = aruco.generateImageMarker(d, 42, 400)          # 400 px marker
img = cv2.copyMakeBorder(img, 50, 50, 50, 50, cv2.BORDER_CONSTANT, value=255)
cv2.imwrite('aruco_marker_42.png', img)              # 500 px total, 80% marker
PY
```

Keep the 80% ratio, or redo the plate-size arithmetic. Check that OpenCV can
read it back before putting it in the world:

```bash
python3 -c "
import cv2, cv2.aruco as a
img = cv2.imread('materials/textures/aruco_marker_42.png', cv2.IMREAD_GRAYSCALE)
det = a.ArucoDetector(a.getPredefinedDictionary(a.DICT_5X5_250), a.DetectorParameters())
print(det.detectMarkers(img)[1])"
```

### Ogre material

`materials/scripts/aruco.material` defines `Aruco/Marker42` pointing at the PNG.
The model references it by `model://aruco_dock_station/materials/...`, which only
resolves if the models directory is on `GAZEBO_MODEL_PATH`. The bringup launch
sets that; if you run `gzserver` by hand you must too:

```bash
export GAZEBO_MODEL_PATH=$(ros2 pkg prefix perceptron_robot_gazebo)/share/perceptron_robot_gazebo/models:$GAZEBO_MODEL_PATH
```

A marker that renders as flat grey almost always means the material script was
not found.

## Adding models

1. `models/<name>/model.config` + `model.sdf`, `<include>` it from the world.
2. If you add files, extend `data_files` in `setup.py` — anything not listed
   there never reaches `install/` and Gazebo will not find it.
3. `colcon build --symlink-install` and relaunch.

---

## Editing the world live

Move things in the Gazebo GUI, then **Edit → Save World As** over
`worlds/docking_world.world`. Faster than editing XML for placement work. Watch
out: Gazebo rewrites the whole file, so re-check that the `gazebo_ros_state`
plugin block survived.
